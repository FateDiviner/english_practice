## 1. 先用一句话理解 RAG

RAG，即 Retrieval-Augmented Generation，检索增强生成。

最简单的理解是：

> RAG 就是把 AI 的闭卷考试改成开卷考试。

没有 RAG 时：

```text
AI 凭训练时记忆回答
```

可能出现两个问题：

1. AI 的知识可能过时或不准确；
2. AI 不知道用户自己上传的教材、笔记和词库内容。

加入 RAG 后：

```text
先检索资料
→ 筛选相关内容
→ 把资料交给 AI
→ AI 依据资料回答
→ 标注引用来源
```

对本项目而言，核心目标是：

> 用户用中文提问，也能从英文资料、词库和词汇关系中找到有依据的答案；找不到时明确说明，而不是编造。

## 2. 一次提问的完整链路

以问题“现在完成时怎么构成”为例。

```text
用户发送问题
   ↓
保存本轮用户消息并读取历史
   ↓
发送 SSE start 帧
   ↓
运行 RAG 管线
   ├─ 判断是否需要检索
   ├─ 清洗问题、抽取关键词、还原指代
   ├─ BM25 按字面检索
   ├─ 向量按语义检索
   ├─ 图谱按词汇关系检索
   ├─ RRF 融合排序
   ├─ 精确词加分重排
   ├─ 阈值过滤
   ├─ 去重
   ├─ 上下文压缩
   └─ 添加引用编号
   ↓
将编号资料注入 system message
   ↓
AI 通过 SSE 流式生成回答
   ↓
返回命中资料来源
   ↓
前端展示回答和来源标签
```

主要代码入口：

| 模块 | 文件 |
| :--- | :--- |
| RAG 总入口 | `backend/app/rag/pipeline.py` |
| 检索前阶段 | `backend/app/rag/stages/pre.py` |
| 三路召回 | `backend/app/rag/stages/retrieve.py` |
| 融合与重排 | `backend/app/rag/stages/ranking.py` |
| 检索后阶段 | `backend/app/rag/stages/post.py` |
| 编排策略 | `backend/app/rag/strategies/base.py` |
| 对话接入 | `backend/app/api/chat.py` |
| Prompt 组装 | `backend/app/ai/prompts.py` |
| 知识库解析与切块 | `backend/app/services/kb_service.py` |
| 语料与索引 | `backend/app/rag/corpus.py` |
| 向量存储 | `backend/app/rag/store.py` |
| Embedding 调用 | `backend/app/rag/embeddings.py` |

## 3. 项目的两层 RAG 架构

项目将 RAG 分成两层：

```text
Strategy：决定整体控制流程
    ↓
Stage：执行单个处理步骤
```

### 3.1 Stage：单个处理步骤

每个 Stage 只负责一件事，例如：

```text
normalize       查询规整
lang_detect     语言判定
intent_gate     意图门控
keywords        关键词抽取
rewrite         指代还原

bm25            词法召回
vector          向量召回
graph           图谱召回

rrf             融合排序
lexical         词法重排
llm             模型重排

threshold       阈值过滤
dedup           去重
compress        上下文压缩
cite            引用标注
```

所有 Stage 的签名统一为：

```python
def stage(ctx: RagContext) -> None:
    ...
```

它们共同读写同一个 `RagContext`，相当于把一张“工作单”依次传给后续阶段。

### 3.2 RagContext：贯穿管线的状态对象

`RagContext` 的主要字段：

| 字段 | 作用 |
| :--- | :--- |
| `query` | 用户原始问题，保持不变 |
| `normalized` | 清洗后的问题 |
| `retrieval_query` | 真正用于检索的问题 |
| `lang` | `zh`、`en` 或 `mixed` |
| `keywords` | 抽取出的关键词 |
| `history` | 最近几轮对话 |
| `candidates` | 当前召回候选 |
| `final` | 最终保留的候选 |
| `context` | 最终注入 AI 的资料文本 |
| `compressed` | 压缩后的资料片段 |
| `trace` | 每阶段耗时与数量变化 |
| `skipped` | 未执行检索的原因 |
| `embedding_calls` | Embedding 调用次数 |
| `notes` | 各阶段产生的诊断备注 |
| `db` | 数据库会话 |

### 3.3 Strategy：控制流程

当前有三种 Strategy。

#### naive

默认策略：

```text
PRE → RETRIEVE → FUSE → RERANK → POST
```

特点：

- 一条直线执行；
- 不循环；
- 不增加额外大模型调用；
- 用来守住首字延迟预算。

#### corrective

简化版 CRAG，即 Corrective RAG：

```text
检索
→ 融合
→ 重排
→ 判断资料质量
→ 如果完全不相关
→ 放宽查询
→ 重新检索
```

当前实现只做：

```text
评分 + 放宽查询 + 重检索
```

不进行网页搜索，原因：

- 外部网页内容不可控；
- 英语学习资料需要稳定、可审计；
- 引入外部搜索会破坏本地优先和零运维目标。

#### self_rag

目前只是占位实现。

真正的 Self-RAG 需要在生成之后判断：

```text
AI 的回答是否被检索资料支持
```

当前没有实现生成后反思。如果配置了 `self_rag`，管线会捕获 `NotImplementedError` 并降级到 `naive`，不会导致对话失败。

### 3.4 注册表和环境变量

阶段通过装饰器注册：

```python
@register_stage(StageKind.PRE, "normalize")
def normalize(ctx: RagContext) -> None:
    ...
```

默认阶段配置：

```ini
RAG_STAGES_PRE=normalize,lang_detect,intent_gate,keywords,rewrite
RAG_STAGES_RETRIEVE=bm25,vector,graph
RAG_STAGES_FUSE=rrf
RAG_STAGES_RERANK=lexical
RAG_STAGES_POST=threshold,dedup,compress,cite
```

这样做的优点：

- 增删阶段不需要修改管线主流程；
- 不同环境可以使用不同组合；
- 调试时可以暂时关闭某个阶段；
- 新增优化通常只需要“写函数、注册、配置启用”。

## 4. 检索前优化

检索前包含两个部分：

```text
资料侧：资料进入知识库之前的准备
查询侧：用户问题进入检索之前的处理
```

---

### 4.1 资料侧：多格式解析

支持格式：

```text
.md
.txt
.pdf
.docx
```

解析规则：

1. UTF-8 优先；
2. UTF-8 失败后尝试 GB18030/GBK；
3. DOCX 同时读取段落和表格；
4. PDF 只提取文字层；
5. 扫描版 PDF 无法提取文字时明确报错；
6. 空文档不入库。

这样设计的原因：

> 如果扫描版 PDF 没有文字层，却显示“上传成功”，用户可能几周后才发现资料根本无法检索。当场报错比事后排查更容易。

---

### 4.2 资料侧：标题感知切块

默认参数：

```text
KB_CHUNK_CHARS=500
KB_CHUNK_OVERLAP=100
```

切块过程：

1. 按 Markdown 标题切分；
2. 按空行切分；
3. 记录所在标题；
4. 超过 500 字的段落使用滑动窗口；
5. 尽量在中文句号、英文句号或换行处断开；
6. 相邻块重叠 100 字。

示例：

```text
标题：现在完成时

正文：
现在完成时由 have 或 has 加过去分词构成，强调对现在的影响。
```

得到的块不只是正文，还包含标题：

```text
heading: 现在完成时
content: 现在完成时由 have 或 has 加过去分词构成……
```

好处：

- 小块比整篇文档更容易命中；
- 引用时能显示“来自 grammar.md 的 #现在完成时”；
- 重叠部分可以降低句子被从中间截断的风险。

---

### 4.3 资料侧：中英混合词条向量化

词库条目被拼成中英混合文本：

```text
abandon /əˈbændən/
v. 放弃；遗弃
They abandoned the plan.
他们放弃了这个计划。
```

同一段文本同时包含：

- 英文单词；
- 音标；
- 中文释义；
- 英文例句；
- 中文例句。

因此可以同时支持：

```text
中文问题 → 命中英文词
英文问题 → 命中中文释义
```

---

### 4.4 资料侧：Embedding 向量化

Embedding 可以理解为：

> 把文字转换成一组数字，使意思相近的文字在数字空间中也相近。

概念示例：

```text
“现在完成时怎么构成”
→ [0.12, -0.45, 0.83, ...]

"The present perfect is formed with have/has..."
→ [0.14, -0.41, 0.79, ...]
```

虽然字面完全不同，但两组数字接近，因此可以命中。

当前配置：

```text
模型：text-embedding-v3
维度：1024
每批最多：10 条
查询缓存容量：512 条
查询缓存有效期：600 秒
请求超时：30 秒
```

批量限制为 10 的原因：

> 当前供应商的批量上限是 10。一次提交 313 个词条会导致接口返回 400，而且该错误在检索时被降级，症状可能只表现为“向量路没有召回”，非常难排查。

项目还刻意没有复用聊天客户端：

```text
聊天客户端：长连接、流式生成
Embedding 客户端：批量、定长、短超时
```

两类调用的错误处理和超时策略不同，分开实现更清晰。

---

### 4.5 资料侧：FAISS 向量存储

项目使用 FAISS 的 `IndexFlatIP`。

可以理解为：

> 把所有资料向量放在一起，新查询来了以后计算相似度，再取最接近的若干条。

计算步骤：

1. 所有向量先做 L2 归一化；
2. 归一化后，内积等于余弦相似度；
3. 越接近 1，语义越相近；
4. 返回分数最高的若干条。

当前语料规模只有几百条到几千条，因此使用精确暴力检索：

```text
优点：没有近似损失
缺点：语料非常大时速度会下降
```

在当前规模下，它比 HNSW、IVF 等复杂索引更简单可靠。

FAISS 主要保存向量，不保存完整的业务元数据，所以项目还保存 sidecar JSON：

```text
kb_chunks.index    知识库向量
kb_chunks.json     向量行号与 chunk 元数据

word_chunks.index  词库向量
word_chunks.json   向量行号与词条元数据
```

---

### 4.6 资料侧：启动预热与首次检索兜底

如果启动时同步完成所有向量化，313 个词条可能需要几十次接口调用，首次请求会卡十几秒。

项目采用双保险：

```text
启动
  ↓
后台 daemon 线程预热
  ↓
同时保留首次检索时的懒加载兜底
```

正常情况：

```text
服务启动
→ 后台建立词库和知识库索引
→ 用户第一次检索时索引已经存在
```

预热未完成或失败：

```text
第一次检索
→ 发现缺少索引
→ 补建索引
→ 继续检索
```

Embedding 完全不可用：

```text
向量路跳过
→ BM25 继续
→ 图谱继续
→ 对话不中断
```

---

### 4.7 查询侧：normalize，查询规整

处理内容：

- 去掉首尾空白；
- 连续空白压成一个空格；
- 全角字符转换半角；
- 保留原始问题；
- 生成用于检索的问题。

示例：

```text
输入：  ＡＢＡＮＤＯＮ
输出：ABANDON
```

为什么需要：

> 全角 `Ａ` 和半角 `A` 是两个不同字符。如果查询保持全角，BM25 按字面匹配时可能完全找不到内容。

三个变量分别为：

```text
ctx.query           用户原话
ctx.normalized      清洗后的问题
ctx.retrieval_query 用于检索的问题
```

原始问题用于展示和日志，检索使用清洗后的版本。

---

### 4.8 查询侧：lang_detect，语言判定

根据中文字符与英文字母比例，将问题分为：

```text
zh      中文
en      英文
mixed   中英混合
```

示例：

```text
现在完成时怎么构成       → zh
present perfect tense    → en
abandon 怎么用           → mixed
```

设计目的：

> 为“中文问题命中英文资料”提供语言基础。

当前状态：

- 判断结果保存在 `ctx.lang`；
- 默认管线尚未用它执行真正的中译英查询改写；
- 当前跨语言能力主要依赖 Embedding 模型本身的跨语言能力。

因此它目前更接近一个预留扩展点，而不是已经完整生效的翻译优化。

---

### 4.9 查询侧：intent_gate，意图门控

这是检索前性价比最高的优化之一。

以下情况跳过 RAG：

```text
空消息
少于 3 个字符
寒暄
短句纠错
短句翻译
短句语法检查
```

示例：

| 输入 | 是否检索 | 原因 |
| :--- | :--- | :--- |
| `hi` | 否 | 输入过短 |
| `thanks` | 否 | 寒暄 |
| `帮我纠正这句话的语法` | 否 | 纠错请求 |
| `please check my grammar` | 否 | 纠错请求 |
| `现在完成时怎么构成` | 是 | 真正询问知识点 |
| `请讲解现在完成时并纠正我下面的句子` | 是 | 内容较长且确实询问知识点 |

纠错跳过有一个长度限制：

```python
any(...) and len(text) < 40
```

它的意义是：

```text
短句纠错 → 跳过
长句知识讲解 + 纠错 → 不跳过
```

一旦 `ctx.skipped` 被设置，`naive` 策略立即返回：

- 后续阶段不执行；
- 不调用 Embedding；
- 不向 AI 注入知识库资料；
- 原有纠错 Prompt 保持不变。

主要收益：

1. 节省检索延迟；
2. 节省 Embedding 调用；
3. 避免无关资料污染原本稳定的纠错能力。

---

### 4.10 查询侧：keywords，关键词抽取

处理规则：

1. 引号中的词优先；
2. 抽取长度至少为 3 的英文词；
3. 抽取连续中文片段；
4. 最多保留 24 个。

示例：

```text
帮我讲讲 "abandon" 这个词
→ abandon 位于关键词列表最前面
```

关键词主要用于：

- `lexical` 精确词加分；
- `graph` 查找词库关系；
- `compress` 找到最相关句子；
- `corrective` 放宽查询。

一个代码细节：

- 注释将中文处理描述为“2-gram”；
- 当前正则是 `[一-鿿]{2,}`；
- 该正则会贪婪匹配连续中文，因此实际更接近“提取整段中文”，不是严格的两字滑动窗口；
- BM25 目前自行重新分词，没有直接使用 `ctx.keywords`。

所以 `keywords` 当前主要服务重排、图谱、压缩和 CRAG，而不是 BM25。

---

### 4.11 查询侧：rewrite，指代还原

场景：

```text`
上一轮：我说的是 "abandon"
这一轮：这个词怎么用
```

直接检索“这个词怎么用”没有价值。

系统会从最近 6 轮对话中寻找最近出现的英文词，将问题还原为：

```text
abandon 怎么用
```

当前只做确定性改写，不调用大模型。

刻意不做拼写纠正，原因：

1. 模型改写会增加首字延迟；
2. 自动纠错可能改错专有名词；
3. 改错后的检索结果可能比不改更差；
4. 拼写错误可以由 BM25 和向量语义相似度部分兜底。

## 5. 检索中优化

默认配置：

```ini
RAG_STAGES_RETRIEVE=bm25,vector,graph
RAG_STAGES_FUSE=rrf
RAG_STAGES_RERANK=lexical
```

---

### 5.1 BM25：按字面找

BM25 可以理解为查目录：

```text
问题：present perfect
资料：The present perfect is formed with...
→ 字面存在 present perfect，因此命中
```

#### 词频饱和

一个词出现一次通常很有价值，但出现 50 次不代表价值高 50 倍。

```text
出现 1 次   → 明显加分
出现 2 次   → 再增加一点
出现 10 次  → 不会无限增加
```

当前参数：

```text
k1 = 1.5
b  = 0.75
```

#### IDF：稀有词更重要

高频功能词：

```text
the、a、of、的
```

几乎每篇资料都有，因此价值低。

稀有词：

```text
present perfect
```

只在少数资料出现，一旦命中价值更高。

#### 长度归一化

长资料天然更容易包含更多词，因此需要对长文本做一定惩罚，避免它仅因为“长”而排名靠前。

#### BM25 缓存

进程内缓存完整 BM25 索引，避免每次查询都重读全部数据。

缓存版本由三个数量组成：

```text
ready 文档数
知识库切块数
active 词数
```

任意数量变化都会重建缓存。

#### BM25 强项

- 精确单词稳定；
- 中文可以按单字匹配；
- 不调用外部接口；
- 速度快；
- 对专有名词和术语可靠。

#### BM25 弱项

- 中文问题查英文资料时字面完全对不上；
- 同义改写容易漏掉；
- 拼写错误会降低命中；
- 无法直接理解语义关系。

因此项目不能只用 BM25。

---

### 5.2 Vector：按意思找

向量召回主要解决跨语言与改写问题。

例如：

```text
中文问题：
现在完成时怎么构成

英文资料：
The present perfect is formed with have/has plus the past participle.
```

两边没有相同关键词，但 Embedding 会使语义表示接近。

流程：

```text
retrieval_query
   ↓
embedding.embed_query()
   ↓
查询向量
   ↓
分别搜索 kb_chunks 和 word_chunks
   ↓
每个集合取 top_k × 2
   ↓
加入 candidates
```

默认 `top_k=6`，因此每个集合最多取 12 条，后续再融合裁剪。

向量路还有两个懒加载入口：

```text
corpus.ensure_kb_index()
corpus.ensure_word_index()
```

正常情况下预热线程已建好索引，这里只是兜底。

#### 失败降级

如果 Embedding 调用失败：

```python
except embeddings.EmbeddingError:
    ctx.notes.append("embedding 不可用，向量路跳过")
    return
```

结果：

- 向量路没有候选；
- BM25 继续；
- 图谱继续；
- 对话不中断。

---

### 5.3 Graph：按词汇关系找

图谱路读取人工维护的 `word_relations` 表。

例如：

```text
abandon
  近义词：give up
  派生词：abandonment
  易混词：abort
```

适用问题：

```text
abandon 的近义词是什么
abandon 和 give up 有什么区别
abandon 常见搭配有哪些
```

处理规则：

1. 从关键词中找 ASCII 英文词；
2. 精确匹配词库中的 active 词条；
3. 查询该词条的关系边；
4. 近义词排在最前；
5. 将词条释义和关系邻居拼成一条候选；
6. 固定分数为 1.0。

特点：

- 不调用大模型；
- 关系由管理端人工维护；
- 没有关系边就没有结果；
- 固定分数使其天然能通过阈值。

它不是完整的 Microsoft GraphRAG：

```text
完整 GraphRAG：
LLM 抽取实体
→ 构建图
→ 社区检测
→ LLM 生成社区摘要

本项目：
人工维护词汇关系
→ 检索时直接查表
```

这样更符合本项目的零运维目标。

---

### 5.4 为什么必须有三路召回

三路各有盲区：

| 方法 | 强项 | 盲区 |
| :--- | :--- | :--- |
| BM25 | 精确词形、术语 | 无法跨语言、怕改写 |
| Vector | 语义、同义、跨语言 | 精确术语可能不如 BM25 |
| Graph | 关系、近义词、派生词 | 没有关系边就没有输出 |

组合后：

```text
字面 + 语义 + 关系 = 互补
```

---

### 5.5 RRF：按名次融合

不同方法的分数无法直接比较：

```text
BM25：可能是 0 到几十
余弦相似度：通常是 0 到 1
Graph：固定 1
```

直接相加没有意义，就像把米、英尺和公里直接相加。

项目采用 RRF，即倒数排名融合：

```text
score = 1 / (60 + 名次)
```

示例：

```text
第 1 名：1 / 61 ≈ 0.0164
第 2 名：1 / 62 ≈ 0.0161
第 3 名：1 / 63 ≈ 0.0159
```

它的核心思想是：

> 不比较原始分数，只比较这条资料在自己这一路中排第几。

`60` 是平滑常数，可以减少第 1 名相对第 2 名的偶然优势。

当前实现：

1. 先按相同正文去重；
2. 同一正文如果被多路命中，只保留最好的名次；
3. 再计算一次 `1/(60+rank)`；
4. Graph 固定为 1.0；
5. 融合后保留 `top_k × 3` 条。

需要注意：

> 当前实现更接近“取同一条资料的最好名次”，不是经典 RRF 中“把同一条资料在多路的分数全部相加”。

因此：

```text
理论经典 RRF：
同一资料三路都第 1 → 1/61 + 1/61 + 1/61 ≈ 0.049

当前实现：
同一正文先合并，只保留最好名次 → 通常仍约为 1/61
```

---

### 5.6 lexical：精确词加分重排

RRF 的盲区是：

> 它只看名次，不知道候选是否真的包含用户点名的词。

示例问题：

```text
abandon 怎么用
```

候选：

```text
A：abandon 的详细释义
B：一段语义相近但没有出现 abandon 的资料
```

lexical 会给包含关键词的内容加分：

```text
每命中一个关键词：+0.05
最大加分：+0.5
```

处理过程：

1. 统计候选中出现的关键词数量；
2. 加分；
3. 重新排序；
4. 裁剪到 `top_k`。

设置上限的原因：

```text
精确命中应该修正 RRF
但不能完全压过语义召回
```

---

### 5.7 LLM 重排：默认关闭

项目还提供模型重排：

```text
把候选资料列给模型
→ 模型给每条打 0 到 1 的相关度
→ 原分数增加 model_score × 0.3
→ 重新排序
```

默认配置：

```ini
RAG_LLM_RERANK=0
```

默认关闭的原因：

> 每次增加一轮模型调用，通常会多等 1 到 2 秒，直接影响首字延迟。

模型重排失败时：

- 记录备注；
- 保留原排序；
- 不影响对话；
- 不丢弃已经召回的资料。

---

### 5.8 corrective：低质量结果重检索

配置：

```ini
RAG_STRATEGY=corrective
```

流程：

```text
检索 → 融合 → 重排 → 评分
                         ↓
                 如果完全不相关
                         ↓
                 放宽查询
                         ↓
                      重新检索
```

评分规则：

```text
最高分 >= 阈值 × 2  → correct
最高分 >= 阈值      → ambiguous
低于阈值           → incorrect
```

只有 `incorrect` 才重新检索。

放宽查询时会去掉：

```text
怎么、什么、帮我、请问、一下、这个、那个、的、吗、呢
how、what、the、a、an
```

只保留实义词。

限制：

- 最多执行 `RAG_CRAG_MAX_ROUNDS` 轮；
- 如果放宽后的查询重复，停止；
- 如果放宽后没有有效词，停止；
- 不执行网页搜索；
- 如果开启 LLM 重排，才会有额外模型调用。

---

## 6. 检索后优化

默认配置：

```ini
RAG_STAGES_POST=threshold,dedup,compress,cite
```

---

### 6.1 threshold：阈值门控

当前阈值：

```ini
RAG_SCORE_THRESHOLD=0.016
```

规则：

```text
最高分低于 0.016
→ 所有候选全部丢弃
→ 不向 AI 注入任何资料
```

原因是：

> 在学习场景中，把无关内容交给 AI，AI 可能顺着无关内容编答案。自信答错通常比坦白说“资料没有覆盖”更危险。

示例：

```text
问题：牛顿第二定律是什么
知识库：全是英语资料
```

两种选择：

| 选择 | 结果 |
| :--- | :--- |
| 强行注入无关资料 | AI 可能建立错误联系 |
| 不注入资料 | AI 明确说明知识库没有覆盖 |

项目选择第二种。

#### 分数标度

RRF 单路第一名约为：

```text
1/61 ≈ 0.0164
```

所以默认阈值必须处于同一量级：

```text
0.016 ≈ 至少在某一路排第一
```

如果错误设置为：

```text
0.15
```

BM25 和向量结果可能全部被挡掉，表象只是“RAG 好像没生效”。

Graph 固定为 1.0，因此天然能过阈值。

#### 当前特点

当前是“最高分决定全体”：

```text
只要最高分过线
→ 整个候选集合进入后续阶段
```

这意味着一条高分资料可能带着几条较弱资料一起注入。这是简单取舍，不是逻辑错误。

---

### 6.2 dedup：近似去重

BM25 与向量可能召回相同或高度相似的段落。

不去重会带来：

1. AI 收到重复内容；
2. 重复内容占掉字符预算；
3. 同一来源看起来像多个独立证据。

处理过程：

1. 转小写；
2. 删除空白；
3. 取前 160 个字符；
4. 计算相似度；
5. 相似度超过 0.8 时丢弃后一条。

当前实现按字符集合计算 Jaccard：

```python
a, b = set(left), set(right)
```

因此它属于近似字符去重，不是严格的单词级或语义级去重。

---

### 6.3 compress：上下文压缩

默认总预算：

```ini
RAG_MAX_CONTEXT_CHARS=3000
```

不能简单从头截断，否则可能得到：

```text
现在完成时由 have 或者
```

这种残缺内容对 AI 不友好。

项目采用“围绕最相关句子开窗”：

1. 把资料拆成句子；
2. 统计哪句话包含关键词最多；
3. 以这句话为中心；
4. 向前保留一句；
5. 向后继续取句；
6. 每块最多约 600 字；
7. 按最终排名依次分配总预算；
8. 如果剩余预算不足 20 字，不保留残缺片段。

结果：

```text
排名靠前的资料优先保留
关键句子优先保留
不会只机械截取开头
不会塞入过短的残句
```

---

### 6.4 cite：引用编号与来源

最终注入 AI 的资料类似：

```text
[1] 来源: grammar #现在完成时
现在完成时由 have 或 has 加过去分词构成……

[2] 词库词条: abandon
abandon /əˈbændən/
v. 放弃，遗弃
……

[3] 词汇关系: abandon
abandon 放弃，遗弃
近义 give up
……
```

来源标签规则：

| 候选类型 | 标签 |
| :--- | :--- |
| 知识库切块 | `来源: 文件名 #小节` |
| 词库词条 | `词库词条: 单词` |
| 词汇关系 | `词汇关系: 单词` |

编号必须与 Prompt 中的指令对齐：

```text
使用了哪条资料，就在回答中标注 [n]。
如果资料没有覆盖，就直接说明。
不能假装资料说了它没有说过的话。
```

为什么要强制引用：

> 如果 AI 标注了 `[1]`，但实际内容与 `[1]` 完全无关，用户核对时会发现张冠李戴。这种情况可能比不引用更糟。

---

## 7. 检索结果如何交给 AI

消息顺序大致如下：

```text
System 1：英语外教人设、纠错规则、引用规则
System 2：当前练习上下文，可选
System 3：RAG 编号资料，可选
History：最近 12 轮对话
User：当前用户输入
```

如果 RAG 没有资料：

```text
rag_context 为空
→ 不追加资料 System 消息
→ 对话行为与没有 RAG 时一致
```

这保证 RAG 不会破坏原有功能：

- 纠错仍按原规则工作；
- 普通聊天仍正常；
- RAG 关闭时不会留下多余状态；
- RAG 故障时不会导致聊天报错。

## 8. 前端如何展示检索状态与来源

对话接口使用 SSE。

典型帧顺序：

```text
start
status: skipped 或 retrieving
status: retrieved
delta × N
done
```

示例：

```json
{
  "type": "status",
  "phase": "retrieved",
  "hits": 3,
  "sources": [
    {
      "index": 1,
      "kind": "chunk",
      "label": "现在完成时",
      "source": "bm25"
    }
  ]
}
```

最终 `done` 帧也携带 `sources`，因此即使中间状态帧丢失，前端仍然可以展示来源。

状态语义：

| 状态 | 含义 |
| :--- | :--- |
| `retrieving` | 正在展示检索状态 |
| `retrieved` | 已命中资料 |
| `skipped` | 已明确跳过，并给出原因 |

前端还会展示：

- 命中资料数量；
- 来源类型；
- 来源标题；
- 回答底部的来源标签。

## 9. 四类核心优化目标

### 9.1 优化“快”

| 优化 | 作用 |
| :--- | :--- |
| 意图门控 | 寒暄和纠错不调用 Embedding |
| 后台预热 | 避免首个请求承担全部索引成本 |
| 首次检索兜底 | 预热失败仍可补建 |
| 查询向量缓存 | 相同问题 10 分钟内不重复调用 |
| BM25 缓存 | 语料未变时不重复读取全表 |
| Embedding 分批 | 避免供应商批量上限导致整体失败 |
| 默认零额外 LLM | 不调用模型改写、排序或反思 |
| FAISS Flat | 当前小语料下毫秒级精确检索 |
| 1500ms 耗时告警 | 发现接近首字延迟预算的检索 |

默认路径通常只有一次 Embedding 调用，没有额外大模型调用。

---

### 9.2 优化“准”

准确率来自多路互补：

```text
BM25    精确词形
Vector  跨语言、同义、改写
Graph   关系、近义词、派生词
RRF     融合不同名次
lexical 精确关键词加分
```

没有任何一种方法全能，因此必须组合。

---

### 9.3 优化“稳”

RAG 不能反过来破坏基础对话。

| 故障 | 实际表现 |
| :--- | :--- |
| Embedding 挂了 | 跳过向量路，继续 BM25 与图谱 |
| 知识库为空 | 正常对话，不注入资料 |
| 三路均无结果 | 正常对话，不注入资料 |
| 最高分低于阈值 | 丢弃全部资料 |
| 配置未知策略 | 返回跳过状态，不阻断对话 |
| 配置 self_rag | 降级到 naive |
| 整条 RAG 管线异常 | 返回空上下文，不冒泡 |
| LLM 重排失败 | 保留原排序 |

总入口 `pipeline.run()` 的核心契约是：

> 任何失败都不应阻断对话。

---

### 9.4 优化“可观测”

项目记录：

- 每阶段耗时；
- 输入候选数；
- 输出候选数；
- 阶段备注；
- 最终排名和分数；
- 最终注入 Prompt 的资料；
- Embedding 健康状态；
- 知识库与词库向量数量。

`StageTrace` 结构：

```text
stage
kind
duration_ms
input_count
output_count
note
```

没有这些数据，阈值和阶段顺序只能盲调。

## 10. 检索前中后优化总表

### 10.1 检索前

| 优化 | 内容 | 防止的问题 |
| :--- | :--- | :--- |
| 多格式解析 | MD、TXT、PDF、DOCX | 资料无法入库 |
| 编码回退 | UTF-8、GB18030 | 中文资料乱码 |
| 标题感知切块 | 保留小节标题 | 引用无法定位 |
| 滑动窗口 | 500 字、100 字重叠 | 句子被切碎 |
| 中英混合词条 | 单词、音标、释义、例句合并 | 中文问不到英文词 |
| Embedding 分批 | 每批最多 10 条 | 批量超限导致整体失败 |
| 后台预热 | daemon 线程 | 首个请求卡住 |
| 懒加载兜底 | 首次检索补索引 | 预热失败后向量路失效 |
| 查询缓存 | LRU 512、TTL 600 秒 | 重复调用 Embedding |
| `normalize` | 全半角和空白规整 | 全角字符搜不到 |
| `lang_detect` | 判断中英混合 | 为跨语言处理提供基础 |
| `intent_gate` | 寒暄、纠错不检索 | 浪费延迟并污染纠错 |
| `keywords` | 引号词优先、英文词抽取 | 不知道用户点名了什么 |
| `rewrite` | 还原“这个词” | 检索无意义代词 |

### 10.2 检索中

| 优化 | 内容 | 防止的问题 |
| :--- | :--- | :--- |
| `bm25` | IDF、词频饱和、长度归一 | 精确词命中不稳定 |
| BM25 缓存 | 语料变化后重建 | 每次查询重读全表 |
| `vector` | 语义和跨语言召回 | 中文查不到英文资料 |
| `graph` | 查人工关系表 | 找不到近义词和派生词 |
| 三路并行 | 字面、语义、关系互补 | 单一方法存在盲区 |
| `rrf` | 按名次融合 | 不同分数量纲无法比较 |
| `lexical` | 精确关键词加分 | RRF 不知道哪个词被点名 |
| `llm` | 可选模型重排 | 默认关闭以保护延迟 |
| `corrective` | 放宽查询并重检索 | 初次查询噪音太多 |

### 10.3 检索后

| 优化 | 内容 | 防止的问题 |
| :--- | :--- | :--- |
| `threshold` | 低于 0.016 全部丢弃 | 无关资料让 AI 顺着编 |
| `dedup` | 近似去重 | 同一段资料占两次预算 |
| `compress` | 关键句窗口、3000 字预算 | 关键句被截断 |
| `cite` | 编号和来源标签 | AI 张冠李戴、无法核对 |
| Prompt 约束 | 要求引用并禁止假装 | 引用与正文不一致 |
| SSE sources | 返回命中来源 | 用户不知道答案依据 |
| 故障降级 | RAG 异常不影响对话 | 检索故障导致聊天不可用 |

## 11. 源码通读发现的现状与缺口

以下问题不影响理解当前设计，但对后续优化非常重要。

### 11.1 删除资料后，向量清理函数未接入业务流程

项目已经实现：

```python
corpus.remove_document_vectors(...)
corpus.remove_word_vectors(...)
```

位置：

```text
backend/app/rag/corpus.py
```

但当前生产代码没有实际调用这些函数。

删除知识库文档时：

```text
删除数据库文档
删除数据库切块
```

但不会立刻删除 FAISS 中的旧向量。

潜在现象：

```text
文档已删除
→ BM25 找不到
→ 向量路仍返回旧 chunk
```

下一次上传新文档时，知识库会整表重建，可能顺带清掉旧向量；但词库向量在服务重启后仍按 ID 增量补齐，已经存在的旧向量不会自动刷新。

这是当前最需要补测试并修复的数据一致性问题。

### 11.2 词内容更新后，旧向量不会自动更新

创建、修改或导入词条时：

- 新词会在懒加载时加入；
- 已存在词的 ID 不变；
- 旧向量仍然存在；
- `ensure_word_index()` 会认为该 ID 已经索引。

因此修改释义或例句后，向量路可能仍使用旧内容。

BM25 缓存也有类似问题：

```text
缓存签名 = 文档数 + 切块数 + 词数
```

如果数量不变、只修改词内容，签名不会变化，BM25 可能继续使用旧缓存。

### 11.3 lang_detect 尚未执行真正的查询翻译

当前能够判断：

```text
zh / en / mixed
```

但默认管线没有根据该结果执行中译英查询改写。

当前跨语言能力主要依赖：

> Embedding 模型本身的跨语言对齐能力。

后续如果要提升中文提问命中英文资料的能力，可以在 `rewrite` 后新增一个可开关的查询翻译 Stage。

### 11.4 RRF 文档描述与实际实现有差异

文档描述偏向经典 RRF 的多路投票求和。

实际代码是：

```text
相同正文先合并
→ 只保留最好名次
→ 计算一次分数
```

因此当前不是严格意义上的“多路各投一票后相加”。

### 11.5 中文 2-gram 描述与实际正则不完全一致

代码注释描述为中文 2-gram，但实际正则会贪婪匹配整段连续中文。

同时，BM25 没有直接使用 `ctx.keywords`，而是自行按英文单词、中文单字分词。

当前 `keywords` 的主要消费者是：

```text
lexical
graph
compress
corrective
```

### 11.6 RAG_TRACE_ENABLED 配置未被业务代码使用

配置存在于：

```text
backend/.env.example
docker-compose.yml
backend/app/config.py
```

但没有发现其他业务代码读取该配置。

当前 `run()` 和管理端 `preview()` 总是构造 trace，该开关暂时不会关闭耗时记录。

### 11.7 阈值目前由最高分决定全体

当前规则：

```text
只要最高分过线
→ 整个候选集合进入后续阶段
```

可能出现：

```text
一条高分资料
+
几条低分资料
→ 一起注入
```

未来可以考虑：

- 逐条阈值；
- 分数加权；
- 高分资料多保留、低分资料少保留；
- 对低分资料使用更严格的内容窗口。

### 11.8 知识库向量化目前是整表重建

新增待索引文档后：

```text
清空整个 kb_chunks
→ 重新嵌入全部 ready 文档
```

当前规模下没有问题，但知识库变大后会产生明显成本。

未来可优化为：

```text
只嵌入新增 chunk
→ 按 document_id 删除旧向量
→ 增量 upsert
```

### 11.9 corrective 缺少专门的循环行为测试

现有测试覆盖：

- corrective 已注册；
- naive 默认路径；
- 阈值和降级；
- 自 RAG 占位降级；
- 默认路径零额外 LLM 调用。

但没有看到专门验证以下行为的测试：

```text
第一轮 incorrect
→ 放宽查询
→ 第二轮重新检索
→ 进入 post
```

如果后续维护 corrective，建议补充该循环测试。

## 12. 如何调试一次检索

### 12.1 使用管理端检索调试页

入口：

```text
管理端 → 检索调试
```

调试页可以查看：

- 当前 RAG 是否启用；
- 当前策略；
- LLM 重排是否开启；
- `top_k`；
- 阈值；
- 上下文预算；
- Embedding 模型；
- 各阶段配置；
- Embedding 是否可用；
- 知识库和词库向量数量；
- 每阶段耗时；
- 输入和输出候选数；
- 最终候选排名与分数；
- 最终注入 Prompt 的完整资料。

调试页与线上对话使用同一条管线，因此调试页看到的排序原则上就是线上排序。

### 12.2 调整阈值时先看分数标度

调整 `RAG_SCORE_THRESHOLD` 前先确认：

```text
BM25 或向量单路第一名约为 0.0164
```

因此阈值应处于 `0.01` 左右的量级，不能直接使用 `0.1` 或 `0.5` 这类没有对应标度的值。

### 12.3 排查“为什么没有检索”

按顺序检查：

```text
1. RAG_ENABLED 是否为 1
2. 是否命中 intent_gate
3. 三路是否召回候选
4. Embedding 是否可用
5. 向量集合数量是否为 0
6. RRF 分数是否低于阈值
7. 是否配置了错误阶段名
8. 是否启用了未实现的 self_rag
```

### 12.4 排查“向量路没有召回”

重点检查：

```text
1. Embedding 接口是否正常
2. 批量大小是否超过供应商上限
3. Embedding 模型维度是否与 RAG_EMBEDDING_DIMENSION 一致
4. 向量索引文件是否存在
5. 文档是否仍是 pending 或 failed
6. 索引是否只补齐了 ID，没有更新旧内容
7. 删除资料后是否残留旧向量
```

## 13. 一句话总结

> 检索前把资料切好、向量化，并把用户问题清洗到适合检索的状态；检索中用 BM25、向量、图谱三路互补，再按名次融合和精确词重排；检索后用阈值拦截无关内容、去重、围绕关键句压缩，最后编号注入 AI，并要求 AI 标注来源；整个过程默认不增加额外大模型调用，任何失败都降级为普通对话。

再压缩成最简单的三句话：

```text
检索前：准备资料，整理问题
检索中：从字面、语义、关系三个方向找
检索后：过滤、去重、压缩、编号，让 AI 有据可查
```
